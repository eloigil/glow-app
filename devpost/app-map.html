GlowApp, mapped

A take-home guide to the finished proof of concept: what the pieces are, how one action flows through the code, and where to start a change. Snapshot of commit 7c4542f on main; it can drift as the code changes.

What it is

GlowApp reads her skin today with YouCam, asks OpenAI for five looks that fix today's points, and teaches the chosen look step by step: each step is her own photo with only the layers so far, painted by YouCam's Makeup try-on.

Screens

app/: /, /photo, /analysis, /looks, /tutorial, /saved. Session lives in memory in lib/session.tsx.

Server routes

app/api/analyze, app/api/looks, app/api/render. They hold the keys and talk to YouCam and OpenAI.

Replay layer

lib/replay.ts: API_MODE replay (default, from fixtures/), record, or live.

On the device

Skin tone in localStorage (lib/toneCache.ts), saved looks in IndexedDB (lib/saved.ts).

One action, end to end: "Start makeup" paints a step

A three-stop route (reference)

Not toured live; a route to follow next time you want to change how steps paint.

  1. Ask for the step imagelib/useStepRenders.ts → renderStep. Posts steps.slice(0, i + 1) with the photo's fileId, so step N always means "layers 1 to N". Results are cached per photo, look and step, so leaving and returning never pays twice.
  2. Turn steps into YouCam effectslib/youcam/effects.ts → toEffect / toEffects. Maps the planner's simple step (category, pattern, colors, intensity, finish) onto YouCam's per-category schema, plus light constant skin smoothing.
  3. Paint or replayapp/api/render/route.ts → POST. Wraps the call in replayable(): replay reads fixtures/render/<hash>.json, live runs the Makeup VTO task, downloads the result and re-encodes it as a JPEG data URL so it never expires.

To change this, start here

  • What counts as one of today's points: POINT_THRESHOLD in lib/youcam/concerns.ts (currently 85; YouCam scores are 1-100, higher is healthier).
  • The kinds of looks and tips the AI writes: the SYSTEM prompt and CORRECTORS in lib/openai/plan.ts; the JSON shape in lib/openai/schema.ts; the model in lib/openai/model.ts.
  • Which makeup shapes it may use: lib/youcam/patterns.json (ids must match YouCam's catalog labels). Changing effects invalidates recorded renders; re-record with API_MODE=record.
  • Error copy: lib/youcam/errors.ts maps YouCam error codes to the messages she sees.
  • Colors, radii, glass: tokens in app/globals.css.

A practice to reuse

Turn an acceptance criterion into a check that runs on every AI answer.

The PRD said every look must fix today's points (prd.md > Step-by-Step Tutorial). The first real plan "passed" by labeling eyebrows as fixing puffy eyes and lipstick as fixing spots. Reading the actual output caught it; the fix made the criterion executable: CORRECTORS plus validate() in lib/openai/plan.ts reject those plans and feed the problems back for one retry, and repair() cleans whatever still slips through (recorded under checklist.md > Revisions).

On the next project with an LLM in the loop: write the rule the output must satisfy, check it in code before anything reaches the screen, and look at a few real outputs early, because a model can satisfy the letter of a prompt and miss its point.

Real APIs and recording

Copy .env.example to .env, add YOUCAM_API_KEY and OPENAI_API_KEY, and set API_MODE=live (nothing saved) or API_MODE=record (saves to fixtures/). Next 16 runs one dev server per folder, so record with npm run build then API_MODE=record npx next start -p 3213 while your dev server keeps running.
